# Audit Teman Rara — 4 Nov 2026

Cakupan: `teman-rara/` (kode, skema, CI, cron-worker), plus dokumen di `APP SETUP/` dan `LAPORAN-PENGERJAAN.md`.
Metode: baca kode langsung. Belum ada yang dijalankan atau diuji di produksi. Poin yang butuh verifikasi ditandai **[verifikasi]**.

## Ringkasan

Fondasinya sehat. Auth berlapis per-resource, validasi Zod di server, file Drive tidak publik, guard idempotensi cron, dan satu fungsi penentu sesi (`getSesiPenghuni`). Tidak ada import cycle.

Masalah terbesar bukan di kode, tapi di tiga tempat:

1. **Loop ke pengelola belum tertutup.** Penghuni bisa daftar, upload bukti, mengadu, dan mengajukan checkout. Tapi pengelola tidak diberi tahu, dan tidak ada yang otomatis. Semua tetap kerja manual di Ops. Ini yang paling menghambat target "efisiensi manpower".
2. **Beberapa kontrol keamanan tidak benar-benar bekerja di Cloudflare Workers** (rate limit di memori, dan identitas klaim akun yang lemah).
3. **Tidak ada jaring pengaman.** Tidak ada test, CI langsung deploy tanpa typecheck, tidak ada monitoring, dan `npm run lint` rusak.

## B. Keamanan

Urutan berdasarkan risiko, bukan nomor.

**B1. Klaim akun hanya butuh nomor kamar + nomor HP.** (`onboarding/actions.ts`)
- Nomor HP penghuni bukan rahasia: tetangga, mantan, dan kontak darurat tahu. Nomor kamar hanya 30 kemungkinan.
- Siapa pun yang klaim duluan menang. Penghuni asli bisa terkunci ("Kamar ini sudah tertaut ke akun lain").
- Akibat klaim: lihat password WiFi, tagihan, dan bisa mengajukan checkout atas nama penghuni.
- Rate limit 5x/15 menit dihitung per akun Clerk. Penyerang cukup buat akun baru.

**B2. Rate limit di memori tidak efektif di Workers.** (`onboarding/actions.ts`, `pendaftaran/actions.ts`)
- Isolate Workers bisa banyak dan sering di-reset, jadi `Map` di memori tidak menahan apa pun.
- Form pendaftaran itu publik, menerima 2 file sampai 2 MB, dan langsung upload ke Drive. Bisa dipakai spam sampai Drive penuh.
- IP diambil dari `x-forwarded-for`, yang bisa dipalsukan. Di Cloudflare yang benar adalah `cf-connecting-ip`.
- Fungsi `cekKetersediaan` juga publik tanpa batas, dan tiap panggilan membaca penuh 3 tabel (`kamar`, `active_tenant`, `booking`). Ini mengamplifikasi biaya baca Turso.

**B3. Validasi tipe file hanya dari `file.type`** (kiriman klien). Tidak ada cek magic bytes. File berbahaya tetap bisa masuk ke Drive dengan label `image/png`. Dampaknya terbatas karena file disajikan `inline` lewat route sendiri, tapi sebaiknya dicek.

**B4. Tidak ada CSP dan HSTS.** Header lain sudah ada.

**B5. Token Google Drive.** Semua upload dan baca memakai satu refresh token OAuth. Komentar kode menyebut "token Google Drive kedaluwarsa" pernah terjadi. **[verifikasi]** Kalau OAuth consent screen di Google Cloud masih berstatus *Testing*, refresh token otomatis mati tiap 7 hari. Ini kandidat root cause kegagalan upload berulang. Solusi: ubah ke *In production*, atau pindah ke service account di Shared Drive.

**B6. Data pribadi sensitif.** KTP/identitas calon penghuni disimpan di Drive tanpa kebijakan retensi. Perlu aturan kapan dihapus (calon yang batal, mantan penghuni). Relevan dengan UU PDP kalau nanti dijual sebagai template.

**B7. Hal yang sudah benar** (jangan diubah): cek kepemilikan file sebelum stream, guard `id_penghuni` di semua update, `DEV_BYPASS_AUTH` dikunci dengan `NODE_ENV`, pesan gagal klaim sengaja seragam, secret tidak masuk repo.

## C. Performa dan efisiensi teknis

1. **Waterfall query di `/kamar`.** `getSesiPenghuni` lalu `getTagihanTerbaru` (2 query berurutan) lalu `getRiwayatBukti`, semua `await` satu per satu. Dua yang terakhir bisa `Promise.all`. `getTagihanTerbaru` bisa jadi satu query dengan subquery. Hemat 2–3 round trip ke Turso per buka halaman.
2. **Koneksi DB.** Memakai WebSocket (`@libsql/isomorphic-ws`). Di Workers yang stateless, handshake terjadi tiap isolate dingin. **[verifikasi]** ukur latency query. Coba URL `https://` (HTTP), Smart Placement di Cloudflare, dan pastikan region Turso dekat Singapura.
3. **`UpdateWatcher` polling tiap 60 detik per tab terbuka.** Tiap polling melewati Clerk middleware dan satu query DB. Kalau 90 penghuni membuka PWA seharian: sampai ±130 ribu request per hari, sementara batas Workers Free 100 ribu per hari. Push sudah ada. Cukup polling saat tab fokus (`visibilitychange`) dan interval 5 menit, atau cek lewat ETag.
4. **Cron tiap 15 menit memakai nama dan path "harian".** Jalannya benar (idempoten), tapi namanya menyesatkan. Jalur juga N+1: tiap tagihan memicu query preferensi dan langganan. Tidak masalah di skala ini, jangan dioptimasi dulu.
5. **Upload berurutan dengan DB.** Drive di-upload dulu, baru insert DB. Kalau insert gagal, file yatim di Drive. Perlu job pembersih atau cukup dicatat.
6. **`ambilGambar` buffer penuh di memori**, sedangkan route dokumen sudah stream. Pada batas 2 MB tidak masalah.
7. **Sumber kebenaran skema ada di repo lain** (`kost-tiga-dara`) dan dipetakan manual di `schema.ts` (termasuk typo `tanggal_selesasi`). Kalau Ops mengubah kolom, Teman Rara rusak diam-diam. Perlu cek otomatis (lihat D4).

## E. Ide efisiensi operasional (sesuai goal "efisiensi manpower")

Karena kamu satu-satunya admin, nilai terbesar ada di sini, bukan di mikro-optimasi kode.

### E1. Notifikasi ke pengelola (paling mendesak)
Sekarang `kirimKePengelola` dialihkan ke ID penghuni lewat env `PENGELOLA_ID_PENGHUNI`, sebagai jembatan sementara. Pendaftaran baru dan bukti bayar bahkan tidak memanggilnya.

| Opsi | Plus | Minus |
|---|---|---|
| Telegram bot | Gratis, setup 30 menit, stabil, tanpa API berbayar | Kamu dan staf harus pakai Telegram |
| WhatsApp via gateway (Fonnte/Wablas) | Semua orang sudah pakai WA | Berbayar kecil, gateway tidak resmi bisa kena blokir |
| WhatsApp Cloud API resmi | Paling aman | Perlu verifikasi bisnis Meta, template pesan, lebih ribet |
| Push di Ops | Tidak butuh kanal baru | Ops beda instance Clerk, belum ada kanal pengelola |

Rekomendasi sementara: Telegram untuk pengelola dulu (murah dan cepat), WA nanti saat bisnis siap.

### E2. Pengingat tagihan lewat WhatsApp, bukan hanya push
Push PWA di iPhone hanya jalan kalau PWA sudah di-install ke layar utama, dan banyak penghuni belum. Kanal yang pasti dibuka orang Indonesia adalah WA. Jatuh tempo dan tunggakan paling cocok pindah ke sini. Ini juga memangkas waktu menagih manual.

### E3. Rekonsiliasi pembayaran otomatis
Alur sekarang: penghuni upload foto → kamu buka Ops → cek mutasi → input pembayaran → verifikasi. Ini sumber "angka tidak match, human error" yang kamu sebut di ABOUT_ME.

| Opsi | Plus | Minus |
|---|---|---|
| Biarkan manual, tapi satu klik verifikasi dari notifikasi (E1) | Paling murah, tidak ada risiko baru | Masih kerja manual |
| QRIS/VA dinamis via Midtrans atau Xendit + webhook | Pembayaran tercatat dan lunas otomatis, angka pasti cocok | Biaya per transaksi, perlu ubah alur Ops, Teman Rara jadi punya hak tulis `payment` |
| Cek mutasi otomatis (parser email m-banking) | Tanpa biaya gateway | Rapuh, tergantung format email bank |

Opsi 2 punya dampak terbesar tapi mengubah aturan "Teman Rara hanya baca" dan menyentuh struktur data. Perlu keputusan kamu sebelum dikerjakan.

### E4. Klaim akun lewat kode sekali pakai (menutup B1)
- Opsi A: staf membuat kode klaim 6 digit per penghuni (di Ops atau kartu fisik saat check-in), dipakai sekali di `/onboarding`.
- Opsi B: OTP WhatsApp ke nomor terdaftar.
- Opsi A lebih murah dan tidak butuh gateway. Opsi B lebih mulus bagi penghuni tapi bergantung E1/E2.

### E5. Kompres foto di sisi klien sebelum upload
Satu perubahan kecil (canvas resize ke ±1600 px, JPEG 0.8) menyelesaikan masalah foto ditolak karena 2 MB, memangkas kuota Drive, dan mempercepat upload di jaringan kos. Tidak butuh dependensi baru.

### E6. Memori ringkasan untuk laporan bulanan keluarga
Data pengaduan, waktu respon, bukti bayar, dan checkout sudah ada di DB. Satu halaman ringkasan (atau PDF bulanan otomatis) mendukung kebutuhanmu soal bukti transparansi ke keluarga dan keputusan berbasis data.

### E7. Pendaftaran → booking → check-in tanpa input ulang
Sekarang calon masuk sebagai booking `Pending` dan staf menyalin data ke Ops. Sebaiknya Ops menarik langsung dari `tr_pendaftaran` saat konfirmasi. Ini perubahan di sisi Ops, bukan di repo ini.
